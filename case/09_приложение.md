# Приложение

Приложение — это не «ещё одна презентация», а **документ-доказательство**: схемы, таблицы, тесты, журнал ИИ и матрица вклада. Жюри читает его до защиты, поэтому все артефакты должны быть здесь, а не только на слайдах.

> **Формат сдачи:** `06_приложение.pdf` в корне папки. Исходный файл `06_приложение.md` также нужно сохранить в Git.  
> **Объём:** 10–15 страниц. Меньше — неполно, больше — жюри может не прочитать.

## Структура приложения

### A. Диаграммы

#### A.1. Схема системы (обязательно)

Нарисуйте в [draw.io](https://www.drawio.com/) или любом другом редакторе схему из 4–6 блоков:

- **Клиент** (приложение клиники) — вызывает сервис.
- **Платёжный сервис** — разрабатываемая система.
- **Эмулятор шлюза** — подсистема, имитирующая эквайринг.
- **Хранилище** (`payments.csv` / `in-memory`) — место хранения платежей.
- **Аудит** — журнал событий.

Стрелки между блоками должны показывать потоки данных. Подпишите, что именно передаётся: JSON-запрос, статус или событие.

**Что показывает жюри:** понимание системы в целом, а не только её кода.

#### A.2. ER-модель (если выполняется бонус `08_ER.md`)

Вставьте диаграмму из `08_ER.md`. Если бонус не выполняется, этот подраздел можно пропустить. В таком случае на слайде 3 файла `05_презентация.md` нужно хотя бы перечислить сущности словами.

#### A.3. Схема состояний платежа (обязательно)

Покажите переходы между статусами платежа:

```text
CREATED ──confirm──► PENDING ──success──► SUCCESS
   │                    │
   │                    ├──decline──► DECLINED
   │                    │
   │                    └──timeout──► PENDING (retry)
   │
   └──cancel──► CANCELED
```

Подпишите, что переводит платёж из одного статуса в другой: подтверждение клиента, код ответа эмулятора или отмена клиентом.

**Что показывает жюри:** понимание идемпотентности и необходимости предотвращать двойное списание.

### B. Таблицы

#### B.1. Правила валидации (из `02_правила.md`)

Вставьте таблицу правил **V-1…V-9** полностью, включая обоснование каждого правила. Это подтверждает, что правила не придуманы произвольно.

#### B.2. Матрица «вход → код ошибки → HTTP» (обязательно)

Заполните матрицу и сверьте её с `02_правила.md` и кодом прототипа.

| Ситуация | Код ошибки | HTTP | Retryable |
|---|---|---:|---|
| Обязательное поле пустое | `VALIDATION_ERROR` | 422 | нет |
| `order_id` не соответствует regex | `INVALID_FORMAT` | 422 | нет |
| … | … | … | … |

Это ключевая таблица: жюри будет сверять её с правилами и реализацией прототипа.

#### B.3. Тесты (из `03_тесты.md`)

Вставьте тесты **T1-1…T1-5** с заполненными полями «Факт» и «Пройден». Если какой-либо тест не пройден, укажите это как есть: честность важнее «зелёной» картинки.

### C. Журнал промптов

Журнал обязателен по регламенту и оценивается в **10 баллов**.

| Дата | Цель | Промпт (кратко) | Результат | Проверка | Использовано |
|---|---|---|---|---|---|
| — | Понять, что такое идемпотентность | «Объясни идемпотентность на примере платежа» | Понятное объяснение | Сверили с глоссарием | Нет, переписали своими словами |
| — | Набросать каркас `validate()` | «Функция validate на Python с проверкой суммы» | Каркас функции | Проверили каждую строку, дополнили правилами V-5…V-9 | Да, переработано |
| … | … | … | … | … | … |

**Правила ведения журнала:**

- Если ИИ не использовали, добавьте одну строку: **«ИИ не использовался»** — и подписи всех участников.
- Если ИИ использовали, добавьте отдельную строку для каждого промпта.
- В колонке «Проверка» укажите, что именно проверили: факт, код, формулу и т. п.
- В колонке «Использовано» укажите один из вариантов: **«да»**, **«нет»** или **«переработано»**.

**Что проверяет жюри:** не количество строк, а то, проверяли ли участники результат и понимают ли его.

### D. Матрица вклада

Заполните матрицу так, чтобы вклад каждого участника был конкретным и заметным.

| Участник | Файлы / задачи | Часы | Подпись |
|---|---|---:|---|
| Иванов И. | `02_правила.md`, `03_тесты.md`, подготовка слайдов 4 и 7 | 12 | ______ |
| … | … | … | … |
| … | … | … | … |
| … | … | … | … |

**Что проверяет жюри:** каждый участник должен выполнить заметную часть работы. Если один человек сделал 80% проекта, это может снизить оценку по критерию «Командная работа» (10 баллов).

### E. Артефакты, которые не поместились в другие файлы

Добавьте в приложение:

- Ссылку на Git-ветку `team_N_case_1`.
- Скриншот последнего коммита.
- Скриншоты вывода прототипа для тестов T1-1 и T1-3 (если прототип есть).
- Скриншот вывода `md5sum 01_данные/payments.csv` как доказательство того, что данные не менялись.

### F. Чек-лист приложения

Перед сдачей проверьте каждый пункт:

- [ ] Схема системы содержит 4–6 блоков, потоки данных подписаны.
- [ ] Есть схема состояний платежа с переходами.
- [ ] Добавлена ER-модель (если выполнялся бонус) или перечислены сущности.
- [ ] Приведены правила V-1…V-9 с обоснованием.
- [ ] Заполнена матрица «вход → код → HTTP → retryable».
- [ ] Добавлены тесты T1-1…T1-5 с фактическими результатами.
- [ ] Есть журнал промптов или запись «ИИ не использовался».
- [ ] Заполнена матрица вклада: 4 участника, задачи различаются.
- [ ] Указаны Git-ветка и коммит.
- [ ] Добавлен скриншот прототипа (если он есть).
- [ ] Файл экспортирован в PDF до начала защиты.

### G. Типичные ошибки (снижают баллы)

1. Приложение представляет собой копию слайдов без подробностей и доказательств.
2. Отсутствует журнал промптов — по регламенту это минус 10 баллов.
3. В матрице вклада указано, что один участник сделал всё, а остальные только «помогали».
4. У тестов не заполнена колонка «Факт», поэтому жюри не может понять, проверяли ли вы решение.
5. Нет схемы системы, из-за чего не видно целостности архитектурного решения.

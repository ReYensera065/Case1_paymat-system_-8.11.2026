# Тест-сценарии платёжного сервиса

**Фактические результаты:** получены при запуске HTTP API-тестов
`api_tests.py` в составе командного прототипа. Все девять сценариев
T1-1--T1-9 пройдены.

## T1-1. Успешная оплата

**Входные данные:** `order_id=ord_1001`, `recipient=clinic_medservice`,
`purpose=Приём терапевта`, `amount=2500.00`, `currency=RUB`.

**Шаги:** 1. Отправить `POST /api/v1/payments` с заголовком
`Idempotency-Key`. 2. Получить `payment_id` и `confirm_token`. 3.
Отправить `POST /api/v1/payments/{id}/confirm` с `method=card_token`.

**Ожидаемый результат:** создание --- HTTP 201, статус `PENDING`;
подтверждение --- HTTP 200, статус `SUCCESS`.

**Фактический результат:** - Создание: HTTP 201, статус `PENDING`,
`payment_id` и `confirm_token` получены. - Подтверждение: HTTP 200,
статус `SUCCESS`. - В истории статусов зафиксированы `PENDING` и
`SUCCESS`.

**Итог:** PASS.

## T1-2. Отказ платёжного шлюза

**Входные данные:** корректные данные платежа; эмулятор настроен на
отказ `INSUFFICIENT_FUNDS`.

**Шаги:** 1. Создать платёж через `POST /api/v1/payments`. 2.
Подтвердить платёж через `POST /api/v1/payments/{id}/confirm`.

**Ожидаемый результат:** HTTP 402, статус `DECLINED`, код
`INSUFFICIENT_FUNDS`.

**Фактический результат:** - Создание: HTTP 201, статус `PENDING`. -
Подтверждение: HTTP 402. - Статус платежа: `DECLINED`. - Код ошибки:
`INSUFFICIENT_FUNDS`.

**Итог:** PASS.

## T1-3. Некорректные входные данные

**Входные данные:** `amount=-100.00`, остальные поля корректны.

**Шаг:** отправить `POST /api/v1/payments`.

**Ожидаемый результат:** HTTP 422, код ошибки `AMOUNT_OUT_OF_RANGE`;
платёж не создаётся.

**Фактический результат:** - HTTP 422. - Код ошибки:
`AMOUNT_OUT_OF_RANGE`. - Платёж не создан.

**Итог:** PASS.

## T1-4. Повторный запрос с тем же Idempotency-Key

**Входные данные:** два одинаковых запроса с одинаковыми `order_id`,
телом и `Idempotency-Key`.

**Шаги:** 1. Отправить первый запрос на создание платежа. 2. Повторить
тот же запрос с тем же ключом.

**Ожидаемый результат:** повтор возвращает сохранённый результат первой
операции; второй платёж не создаётся; HTTP 200, код `DUPLICATE_REQUEST`.

**Фактический результат:** - Первый запрос: HTTP 201. - Повторный
запрос: HTTP 200. - В обоих ответах одинаковый `payment_id`. - Повтор
вернул сохранённый результат; второй платёж не создавался.

**Итог:** PASS.

## T1-5. Таймаут платёжного шлюза

**Входные данные:** корректные данные платежа; эмулятор настроен на
`TIMEOUT`.

**Шаги:** 1. Создать платёж. 2. Подтвердить его через
`POST /api/v1/payments/{id}/confirm`. 3. Проверить платёж через
`GET /api/v1/payments/{id}`.

**Ожидаемый результат:** подтверждение возвращает HTTP 504; статус
платежа остаётся `PENDING`; в журнале фиксируется `TIMEOUT`.

**Фактический результат:** - Создание: HTTP 201. - Подтверждение: HTTP
504, код `TIMEOUT`, статус `PENDING`. - Получение статуса: HTTP 200,
статус `PENDING`. - Повтор подтверждения с тем же `Idempotency-Key`:
HTTP 200. - В журнале для данного платежа зафиксирован один вызов шлюза.

**Итог:** PASS.

## T1-6. Повторное создание заказа

**Входные данные:** одна и та же пара `order_id` и `recipient`; для
второго запроса используется новый `Idempotency-Key`.

**Шаги:** 1. Создать платёж. 2. Повторно отправить запрос создания
платежа с теми же `order_id` и `recipient`, но с новым ключом.

**Ожидаемый результат:** HTTP 409, код `DUPLICATE_ORDER`; второй платёж
не создаётся.

**Фактический результат:** - Первое создание: HTTP 201. - Повторное
создание с новым ключом: HTTP 409. - Код ошибки: `DUPLICATE_ORDER`. - В
хранилище обнаружена одна запись для этой пары `order_id + recipient`.

**Итог:** PASS.

## T1-7. Получение информации о платеже

**Входные данные:** существующий `payment_id`.

**Шаг:** отправить `GET /api/v1/payments/{id}`.

**Ожидаемый результат:** HTTP 200; ответ содержит `payment_id`,
`status`, `amount`, `currency` и историю изменения статусов.

**Фактический результат:** - Создание тестового платежа: HTTP 201. -
Получение информации: HTTP 200. - Возвращены `payment_id`, статус
`PENDING`, сумма `2500.00`, валюта `RUB`. - История содержит запись со
статусом `PENDING`.

**Итог:** PASS.

## T1-8. Отмена платежа

**Входные данные:** созданный, но ещё не подтверждённый платёж.

**Шаги:** 1. Отправить `POST /api/v1/payments/{id}/cancel`. 2. Повторно
запросить платёж через `GET /api/v1/payments/{id}`.

**Ожидаемый результат:** HTTP 200; статус платежа `CANCELED`; при
повторном получении информации статус остаётся `CANCELED`.

**Фактический результат:** - Создание: HTTP 201. - Отмена: HTTP 200,
статус `CANCELED`. - Повторное получение: HTTP 200. - Текущий статус
остался `CANCELED`. - История статусов содержит `PENDING` и `CANCELED`.

**Итог:** PASS.

## T1-9. Проверка получателя со статусом INACTIVE

**Входные данные:** корректные данные платежа; `recipient` существует в
`recipients.csv`, но имеет статус `INACTIVE`.

**Шаг:** отправить `POST /api/v1/payments`.

**Ожидаемый результат:** платёж отклоняется с кодом
`RECIPIENT_NOT_FOUND`; запись платежа не создаётся.

**Фактический результат:** - HTTP 404. - Код ошибки:
`RECIPIENT_NOT_FOUND`. - Сообщение: `Recipient not found or inactive.` -
Количество платежей в хранилище до запроса и после запроса не
изменилось: 12.

**Итог:** PASS.
